## 1. 背景

### 1.1 现状

「焦外述影」官网是一个**常青招新落地页**（React + Vite 纯静态站），部署在 **Vercel**，域名 `hhxyjwsyst.online`。全站文案与素材路径收拢在 `src/config/site.ts` 单一数据源中，图片视频在 `public/` 目录。

网站的**内容更新动作**与**网站开发能力**目前集中在同一个人身上：任何改动（哪怕只是换一张二维码图片）都需要改代码 → git 提交 → 构建发布。

### 1.2 组织事实（2026-10 与管理组访谈确认）

- 管理组共 4~5 人：现任社长、周弘旭（部长）、喵喵（拍照部长）、吴长轩（前任社长，顾问），**均非职业开发者**；
- 素材源头已存在：相机拍摄在知楼 A403 办公地导卡，手机拍摄微信传原图；社团已有**本地部署的私有 NAS** 作为公共素材库；
- 作品上线流程：活动后筛选约 30~50 张 → 精选 → 管理组一对一对接拍摄者 → 上首页；
- 首页（橱窗）内容**半学期大改一次**；
- 微信纳新群二维码**约 7 天过期一次**，过期前需手动更换；
- 公众号、抖音、网站、NAS 四个渠道各自独立，入口分散。

## 2. 痛点

| 编号 | 痛点 | 影响 | 现状佐证 |
| --- | --- | --- | --- |
| PT-1 | **换群码依赖开发者**。群码 7 天过期，而换码动作只有持有代码仓库的人能完成 | 招新关键期若开发者不在，新同学扫到过期码 → **转化直接归零**。这是当前最高优先级痛点 | 微信群原话：「网站在你手里，你才能弄」 |
| PT-2 | **橱窗更新无自主权**。半学期一次的作品更换、文案调整，管理组无人能独立完成 | 内容更新节奏被开发者个人日程绑架；社团活力无法及时呈现 | 半学期一次的更新至今未由管理组完成过 |
| PT-3 | **多渠道入口分散**。公众号后台、抖音、NAS、网站各自独立，无统一管理视图 | 管理组交接与日常运维成本高，新任部长需要逐个问入口 | 吴长轩：「公众号、网站、抖音之间可以有关联，管理可以放在网站上」 |
| PT-4 | **改动无版本、无回滚**。现状直接改源文件，改错只能靠开发者记忆恢复 | 一次误改可能让招新首页长时间处于异常状态 | git 历史对管理组不可见、不可操作 |
| PT-5 | **知识集中于单人**。网站维护知识（怎么改、怎么发、素材规格）没有文档化传承机制 | 开发者毕业/退出后站点变"死站"，与「常青门户」定位矛盾 | 项目 Credits 中开发角色仅一人 |

## 3. 产品目标与成功指标

### 3.1 产品定位（一句话）

**管理组 4~5 人的「橱窗编辑台」**：把已经精选好的内容，无需开发者、无需懂代码地挂上官网；并把换群码这个高频运维动作变成手机上的一分钟操作。

**明确不是**：全员投稿系统、公共网盘（NAS 已承担）、内容创作工具。

### 3.2 目标与指标

| 编号 | 目标 | 成功指标 |
| --- | --- | --- |
| G-1 | 群码更换完全自助 | 管理组任意成员在**手机上 5 分钟内**（含发布等待）独立完成换码；因群码过期导致的"无法进群"时长为 **0** |
| G-2 | 橱窗更新完全自助 | 半学期大更新全程**开发者介入次数 = 0** |
| G-3 | 可回滚 | 任何一次内容变更都可在一分钟内回退到此前任一版本 |
| G-4 | 可传承 | 《管理组使用说明》覆盖全部高频操作，新任管理组成员照文档即可上手 |

## 6. 技术方案概述（功能需求的实现前提）

> 架构定稿（2026-10-25，与社长确认）：**成员不注册 GitHub，不引入 Sveltia / Cloudflare**，
> 编辑层为自建极简后台——账号密码登录，界面即已确认的原型设计。

- **内容层**：全站可编辑内容抽为 `src/content/*.json` 结构化文件（brand / hero / gallery / endorsements / qrs），字段名与现有 `site.ts` 数据一一对应；`site.ts` 保留为"读取层 + TypeScript 类型"，页面组件不感知变化。
- **编辑层**：`/admin` 下的自建后台页面（单页，复用原型视觉），登录方式为**账号 + 密码**（每人一个账号，密码存 Vercel 环境变量，无数据库）。
- **服务层**：Vercel Serverless 函数（`api/login.js`、`api/content.js`，零第三方依赖）：登录校验（签名 Cookie + 登录限速）、内容读写、图片上传、发布历史。写入通过 **GitHub Contents API 以机器人身份提交**（Fine-grained PAT，仅内容目录写权限）。
- **发布**：提交进入 GitHub 仓库 main 分支 → Vercel 自动构建 → **约 3 分钟内全网上线**。
- **迁移预留**：JSON schema 保持稳定。将来若迁至"社团电脑自建后端 + 内网穿透"，仅需替换 `/api/content` 的写入目标（GitHub API → NAS 文件），后台页面与前台组件零改动。

## 7. 功能需求

> 优先级标注：P0 = 首个交付必须包含；P1 = 第二批次；P2 = 验证有人用之后再做。

### FR-1 登录与权限（P0）

- **入口**：`https://hhxyjwsyst.online/admin`。
- **流程**：打开后台 → 输入账号 + 密码 → 登录 → 进入编辑界面（会话有效期 7 天）。
- **规则**：
  - **每人一个账号**（如 miaomiao / zhouhongxu），账号与密码由仓库 Owner 配置在 Vercel 环境变量 `ADMIN_ACCOUNTS`（JSON 格式）中，不建数据库；
  - 密码不落库不入 Git；登录态为 HttpOnly 签名 Cookie（HMAC），前端不存密码；
  - 登录接口带**限速**（同 IP 连续失败 5 次锁定 10 分钟）防爆破；
  - 发布记录中的操作者 = 登录账号。
- **异常**：连续失败超限提示"稍后再试"；忘记密码找开发者重置环境变量。

### FR-2 二维码管理（P0）

管理四个进群/关注通道的二维码图片与文案：

| 通道 key | 标签 | 说明 |
| --- | --- | --- |
| `wx` | 微信群 · 纳新群 | 主通道，约 7 天过期，最高频更换 |
| `qq` | QQ 群 · 纳新群 | 新增通道（本期加入），群码长期有效 |
| `mp` | 官方公众号 | 低频 |
| `dy` | 官方抖音 | 低频 |

- **操作**：在后台「二维码」集合中选中通道 → 上传新图片（或替换文字说明）→ 保存。
- **规则**：
  - 图片须为方形码体（若从微信海报截取，需裁切为方形）；
  - 单图 ≤ 2MB，格式 JPG/PNG；
  - 保存后自动提交并发布，约 3 分钟全网生效（界面明示"发布中"状态）；
  - 前台显影盘（S9）与扫码区自动展示新图，无需其他操作。
- **异常**：见 EB-2、EB-3、EB-7。

### FR-3 橱窗内容管理（P1）

覆盖以下展示位的内容与图片：

| 模块 | 可编辑内容 |
| --- | --- |
| 首屏轮播（hero） | 4~5 张轮播图（**第一张为首屏 LCP 图，更换时必须同步保证加载性能**，规格见 8.7） |
| 数字带（stats） | 4 条事实的数值与说明文字 |
| 四季横滑 | 四季名称、描述、配图 |
| 作品位 | 9 个作品位的图片与一句话说明 |
| 背书 | 官方转发/表彰/党媒报道卡片（图片、视频封面、文字） |
| 关于我们 | 配图、介绍段落 |
| 精选短片 | 视频文件、封面、说明 |

- **规则**：
  - 图片上传统一进入 `public/photos/`、`public/videos/` 对应目录，后台界面标注压缩规格建议（长边 ≤ 2000px、≤ 2MB）；
  - 作品说明**默认不署名**（隐私原则沿用现有站规），如需署名由管理组在说明末尾手动添加「· 姓名 摄」；
  - 所有列表支持新增/删除/排序（如轮播图顺序、作品位增减）。

### FR-4 文案管理（P1）

- 覆盖：品牌信息（社团名/slogan/眉题/介绍段落/标签）、联系方式（微信/邮箱）、FAQ 六条、页面 SEO 所需的 `siteUrl`；
- `siteUrl` 字段标注为"开发者字段"，默认锁定不展示给普通编辑者（改错会导致分享卡失效）。

### FR-5 发布历史与回滚（P0）

- 每次保存自动生成一条带作者、时间、改动摘要的发布记录（Git 提交）；
- 任何记录可一键回滚（回滚 = revert 提交并再次自动发布，约 3 分钟生效）；
- 使用说明中写明回滚操作路径，确保非技术成员可执行。

### FR-6 渠道管理面板（P2，可选）

- 一个汇总页（可与后台首页合并）：公众号后台、抖音后台、NAS、GitHub 仓库、本后台的**链接入口 + 负责人 + 常用二维码**；
- 目标是落实"管理放在网站上"，降低 PT-3、PT-5 的交接成本。

## 8. 错误兜底与降级

> 原则：**前台永不因内容层的任何故障而白屏**；后台故障必须有绕过路径，且绕过路径写进使用说明。

| 编号 | 故障场景 | 兜底机制 |
| --- | --- | --- |
| EB-1 | JSON 内容字段缺失、类型错误、文件损坏 | 前台读取层对每个字段做校验，异常时回退到**打包内置的默认值**（即当前线上内容快照）；页面正常渲染，不白屏、不出 `undefined` |
| EB-2 | 图片路径 404（文件被误删/改名） | 沿用现有占位框机制：`src: null` 或加载失败时显示占位框（含该位置名称与规格提示），布局不塌 |
| EB-3 | 构建失败（如 JSON 语法错误、资源超限） | Vercel 保留**最近一次成功部署**继续服务，线上不中断；失败通知进入仓库 Actions 记录；使用说明写明"保存后 10 分钟未见生效 = 构建可能失败，联系开发者或检查上次改动" |
| EB-4 | 后台服务故障（登录异常 / api 函数出错 / 环境变量失效） | **绕过路径**：开发者直接在 GitHub 网页端（手机 App 亦可）编辑对应 JSON 文件或上传替换二维码图片 → 提交后同样触发自动部署。此路径写入使用说明，保证后台全挂时换码仍可行 |
| EB-5 | 误删/误改内容 | Git 历史回滚（FR-5）；内容文件与图片均在版本库中，删除可恢复 |
| EB-6 | 上传超大图 / 格式错误 | CMS 侧做格式与大小提示；即使超大图入库导致页面变慢，前台图片为懒加载，首屏 LCP 图之外的图片不影响首开 |
| EB-7 | hero 第一张图被换成大体积图片，LCP 劣化 | 使用说明将首屏图规格（建议 ≤ 500KB）标注为**硬性提示**，并在后台该字段描述中明示；兜底依赖 EB-5 回滚 |
| EB-8 | Vercel 平台整体不可用期间群码过期 | 极端场景：管理组在公众号/朋友圈发布新群码图片作为临时通道；联系方式页的微信号（ZWCX3690）始终可用，访客可手动添加 |
| EB-9 | 未来迁移到自建后端（社团电脑 + 内网穿透） | JSON schema 即迁移契约：后端只需按同一 schema 写文件；若改为运行时读取，读取层已内置 fetch + 静态兜底双通道，前台组件不变 |
| EB-10 | 管理组人员变动 / 账号密码泄露 | 仓库 Owner 增改 `ADMIN_ACCOUNTS` 环境变量并重新部署即可完成权限交接与重置；开发者保留 GitHub 直改兜底路径 |

## 10. 风险与开放问题

| 编号 | 风险/问题 | 应对 |
| --- | --- | --- |
| R-1 | 自建服务端代码的安全面（登录爆破、Token 泄露） | 登录限速 + 签名 Cookie；Fine-grained PAT 仅授予仓库 Contents 写权限；密码与 Token 只存 Vercel 环境变量，不入 Git |
| R-2 | 3 分钟发布延迟被误认为"没保存上" | 后台界面与文档明示"发布中"状态与生效时间预期 |
| R-3 | QQ 群号/群码素材尚未提供 | JSON 中先以占位（null）接入，素材到位后由管理组自行上传——这本身是后台的第一次实战 |
| R-4 | 视频若日后体积增大，Git 仓库膨胀 | 本期约束橱窗视频为压缩成品；超过阈值（单文件 > 50MB）时触发讨论是否启用 NAS 外链或自建后端路线 |
| R-5 | 前台各组件目前直接 import `site.ts` 常量，需要确认无组件在模块顶层对数据做复杂变换 | 实施时逐一核对引用组件；读取层保证导出形态与现状完全一致 |
