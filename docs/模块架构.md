# 模块架构说明

> 范围：管理后台相关模块（`api/`、`public/admin/`、`src/content/`、`src/config/site.ts`）。
> 关系标注语法：**A →（关系）→ B**，关系四类：
> - **依赖**：A 的正确运行需要 B 存在（编译期/装配期确定）
> - **调用**：A 在运行时主动请求 B（B 可替换）
> - **触发**：B 的变化自动引发 A 执行（事件/钩子）
> - **实现**：A 是某接口约定的具体实现（箭头指向接口）

## 一、核心模块清单（每模块一句话职责）

| 模块 | 职责 |
| --- | --- |
| `src/content/*.json` | 全站可编辑内容的唯一事实源（五个文件，后台写入目标） |
| `src/config/site.ts` | 内容读取层：校验清洗 JSON 并逐字段兜底，对前台组件暴露稳定的类型化数据出口 |
| 前台区块组件（`src/sections/` 等） | 渲染页面，只消费 `site.ts` 导出的数据与类型 |
| `public/admin/index.html` | 管理后台单页：登录态探测、四屏交互、上传/保存/回滚的全部操作入口 |
| `api/login.js` | 账号密码校验、限速、签发 HttpOnly 签名 Cookie |
| `api/content.js` | 内容业务编排：白名单校验、幂等短路、回滚，全部读写经由存储接口 |
| `api/_lib.js` | 共享内核：会话签名/校验、登录限速，以及 **StorageAdapter 接口约定 + GitHub/本地两个实现** |
| GitHub 仓库（main 分支） | 持久层：内容 JSON、媒体文件、提交历史（发布记录与回滚的基础） |
| Vercel 平台 | 托管与发布：静态前台 + Serverless 函数 + push 触发的自动构建（约 3 分钟生效） |
| `.github/workflows/compress-media.yml` | 媒体守门：PR 中超规格图片自动压缩回推 |

```
 管理组手机
    │

    │                                   │
    │  调用（携带 Cookie）               └─依赖──▶ _lib.js（verifySession 校验签名）
    ▼

    │                          ▲
    │                          ├──实现──▶ GitHubStorage（Contents API，生产）
    │                          └──实现──▶ LocalStorage（本地文件，迁移演练）
    ▼ （调用：Contents API，机器人 PAT）

    ▲                                     │
    │                                     ▼

    │                                                           ▼ 依赖（构建期打包）
    └──承载──▶ src/content/*.json ◀──读取/写入（经由存储接口）──…（JSON 即契约）
```

## 三、关系明细与理由

| 关系 | 理由 |
| --- | --- |
| 前台组件 →（依赖）→ `site.ts` | 组件只见类型化出口，不见 JSON 细节；数据源怎么变（文件/接口）组件无感 |
| `site.ts` →（依赖）→ `content/*.json` | 构建期打包进产物：微信端零额外请求，且 JSON 损坏时用内置兜底值，前台永不白屏 |
| `admin/index.html` →（调用）→ `api/login.js` / `api/content.js` | 后台只走 HTTP 接口，不接触任何存储凭据；接口报错以中文 toast 呈现 |
| `api/content.js` →（依赖）→ `getStorage()` 返回的 **StorageAdapter 接口** | **依赖倒置**：业务规则（白名单、幂等、回滚语义）不随存储技术变化；迁 NAS 只加实现、切换环境变量，`content.js` 零改动 |
| `GitHubStorage` / `LocalStorage` →（实现）→ StorageAdapter 接口 | 两个可替换实现；`STORAGE_ADAPTER` 环境变量是唯一选择点（装配在 `_lib.getStorage()`） |
| `GitHub main 收到提交` →（触发）→ Vercel 自动构建 | 发布链路无需任何人工/脚本干预；构建失败保留上次成功部署（前台不中断） |
| `GitHub main 收到提交` →（触发）→ 后台「发布自动确认」轮询 | 后台每 20s 查询 history 接口，出现新提交即提示「已上线」，消除 3 分钟不确定感 |
| PR 含 public/ 图片 →（触发）→ compress-media Action | 把"≤2MB/长边≤2000px"从文档约定变成强制机制 |
| `qrs.json` 的 `wxExpires` →（触发）→ 后台概览倒计时 | 数据驱动预警：过期日一变，概览红黄状态自动更新，无需额外状态存储 |

## 四、依赖倒置落点（摘要）

1. **服务端**：`content.js`（业务）持有的是 `getStorage()` 注入的适配器，签名即接口契约（`getFileMeta / getFileBase64 / putFile / readJsonFile / listCommits`）。新存储 = 新实现 + 一行环境变量。
2. **前台**：组件依赖 `site.ts` 的导出签名（"内容接口"），JSON 只是当前实现；读取层内联兜底值相当于接口的默认实现。
3. **后台前端**：仅依赖 `/api/*` 的 HTTP 契约（请求/响应结构见技术方案 §4），不依赖函数内部实现。
